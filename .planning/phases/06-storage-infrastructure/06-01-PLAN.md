Create the `supabase/migrations/` directory if it does not exist.

Write a SQL migration file with the following, in order:

1. **Create bucket** (idempotent — wrap in DO block or use INSERT ... ON CONFLICT):
   ```sql
   INSERT INTO storage.buckets (id, name, public)
   VALUES ('uploads', 'uploads', true)
   ON CONFLICT (id) DO NOTHING;
   ```

2. **Public read policy** (anyone can read — logos and avatars are public content):
   ```sql
   CREATE POLICY "Public read access"
   ON storage.objects FOR SELECT
   TO public
   USING (bucket_id = 'uploads');
   ```

3. **Profile path policies** (INSERT, UPDATE, DELETE) using `auth.uid()` path-prefix scoping:
   - INSERT with `WITH CHECK`: `bucket_id = 'uploads' AND (storage.foldername(name))[1] = 'profiles' AND (storage.foldername(name))[2] = auth.uid()::text`
   - UPDATE with `USING`: same conditions
   - DELETE with `USING`: same conditions

4. **School path policies** (INSERT, UPDATE, DELETE) using sub-select to verify school ownership:
   - INSERT with `WITH CHECK`: `bucket_id = 'uploads' AND (storage.foldername(name))[1] = 'schools' AND EXISTS (SELECT 1 FROM public.schools WHERE id = (storage.foldername(name))[2]::uuid AND creator_id = auth.uid())`
   - UPDATE with `USING`: same conditions
   - DELETE with `USING`: same conditions

CRITICAL NOTES (from research pitfalls):
- PostgreSQL arrays are 1-indexed: use `[1]` for first segment, `[2]` for second
- All 3 operations (INSERT, UPDATE, DELETE) are needed for upsert to work on second upload
- Policy names must be unique — use descriptive names like "Creator can upload own avatar", "Creator can update own school logo", etc.
- Add a comment at the top of the file explaining this is for Phase 6 storage infrastructure


**`getSignedUploadUrl(path: string): Promise<SignedUploadResult>`:**

1. Import `createClient` from `@/lib/supabase/server` (async server-side client with cookie auth).
2. Call `supabase.auth.getUser()` — if no user, return `{ data: null, error: 'Unauthorized' }`.
3. **Ownership validation:**
   - If path starts with `profiles/`: verify `path.split('/')[1] === user.id`. Reject if mismatch.
   - If path starts with `schools/`: extract `schoolId = path.split('/')[1]`, query `supabase.from('schools').select('id').eq('id', schoolId).eq('creator_id', user.id).single()`. Reject if no result.
   - Any other prefix: reject with `'Invalid path prefix'`.
4. Call `supabase.storage.from('uploads').createSignedUploadUrl(path, { upsert: true })`.
5. If error, return `{ data: null, error: error.message }`.
6. Return `{ data: { signedUrl: data.signedUrl, token: data.token, path }, error: null }`.

**`getPublicStorageUrl(path: string): string` (non-async helper, exported):**

This is NOT a Server Action (no 'use server' needed for individual exports — the file-level directive covers all). However, this function uses the **browser** Supabase client since it's synchronous and will be called client-side. 

IMPORTANT: Move this helper to a separate non-server-action file to avoid issues. Create it as a plain utility:

Actually, `getPublicUrl` is synchronous and can be computed without any Supabase client — it's just URL construction. Implement it as a pure function:

```typescript
export function getPublicStorageUrl(path: string): string {
  const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL;
  return `${supabaseUrl}/storage/v1/object/public/uploads/${path}`;
}
```

This avoids needing the browser client in a server action file. The `NEXT_PUBLIC_SUPABASE_URL` is available in both client and server contexts. This matches the URL format Supabase uses for public bucket objects.

**No new dependencies required.** All imports (`createClient` from `@/lib/supabase/server`) are already available.
