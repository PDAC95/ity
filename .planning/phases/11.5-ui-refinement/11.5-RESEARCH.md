## Summary

Phase 11.5 is a pure UI refinement pass — no new functionality, only visual polish. The goal is to unify the dark theme across all surfaces (auth pages, dashboard shell, chat wizard, forms) so the product feels coherent and premium instead of a prototype assembled from different eras of styling.

The codebase analysis reveals a **split personality**: the `dashboard-shell.tsx` (recently redesigned by the user) already uses a good dark aesthetic with bg-black outer shell, zinc-900 cards, and the pastel-colored dock. However, the **auth pages** (`login`, `register`, etc.) still use light/gray Tailwind (`text-gray-900`, `border-gray-300`, `bg-blue-600`) — a completely different visual language. The **chat wizard** uses light surfaces (`border-zinc-100`, `bg-zinc-50`, `text-zinc-900`) as a Claude-style light chat. The **form cards** (profile, school setup) are partially dark but use `indigo-600` accent color instead of the locked pastel blue `#bfdbfe`. The **template gallery** already has good dark bones but uses `indigo-600` for active filter pills.

The unification work is mechanical but must be applied to every component surface. Key libraries already present: `tailwindcss-animate` (shimmer animations), `framer-motion` (message entry animations), `sonner` (toast notifications — needs custom theming to match zinc-800). No new library installations required.

**Primary recommendation:** Execute as 4 focused passes (Auth, Dashboard+Forms, Chat Wizard, Polish/Skeletons). Each pass targets specific files listed in the Architecture section. No Tailwind config changes needed — all target colors are native zinc values or arbitrary values already used in the project.

Apply to all inputs in auth pages, profile, school-setup:

    'block w-full rounded-lg border bg-zinc-800 px-3 py-2.5 text-sm text-zinc-100',

## Common Pitfalls

### Pitfall 1: Content Area Background Cascade
**What goes wrong:** Changing `dashboard-shell.tsx` content area from `#f8f8f8` to `#1e1e22` makes all child pages work on dark bg. But components that hard-code `text-zinc-900` (dark text for light bg) become invisible.
**Why it happens:** Components were written assuming light content area.
**How to avoid:** After changing the content area bg, do a grep for `text-zinc-900` and `text-gray-900` in all dashboard child components to find visibility issues.
**Warning signs:** Text disappears or is very hard to read after the change.

### Pitfall 2: Sticky Filter Bar Background Mismatch
**What goes wrong:** `template-gallery.tsx` sticky filter bar uses `bg-zinc-950` — this was tuned for the old light content area to look like a "floating" bar. On dark content area it will blend in or look wrong.
**Why it happens:** Template gallery was built expecting dark bg but the shell was light.
**How to avoid:** Update sticky bar to use the actual content area bg (`#1e1e22`) or `bg-zinc-900/90 backdrop-blur-sm`.

### Pitfall 3: Sonner Toast Position
**What goes wrong:** Sonner `<Toaster>` default renders with default light styling. Theming requires props on the `<Toaster>` component, not on individual `toast()` calls.
**Why it happens:** The `Toaster` component is likely placed in `app/layout.tsx` — check there and update.
**How to avoid:** Find the Toaster in `app/layout.tsx`, add `toastOptions` with zinc classNames.

### Pitfall 4: Notch SVG Fill Color
**What goes wrong:** The notch in `dashboard-shell.tsx` uses `fill="#f8f8f8"` to visually connect the nav notch with the content bubble. If the content area bg changes, the notch fill must change too.
**Why it happens:** It's a visual illusion — the SVG "notch" color must exactly match the content area bg.
**How to avoid:** Change notch `fill` from `#f8f8f8` to `#1e1e22` in the same commit as the content area change.

### Pitfall 5: Chat Stepper State Complexity
**What goes wrong:** Tracking the "current step" in the chat wizard requires knowing what questions have been answered. LLM responses don't have structured step metadata.
**Why it happens:** The wizard is free-form conversation, not a structured wizard with explicit step transitions.
**How to avoid:** Use turn count heuristic (e.g., `Math.min(Math.floor(userTurnCount / 3) + 1, 5)`) as a simple proxy. The CONTEXT.md says progress stepper with numbered steps — implement as visual decoration tracking message count, not actual step completion. This is pure UI.

### Pitfall 6: Auth Layout Background Color on Mobile
**What goes wrong:** Auth layout right panel is currently plain white. On mobile, there's no left panel. The entire screen is white. Changing to dark zinc-900 must also update the root `<html>`/`<body>` bg or there will be a white flash.
**Why it happens:** `globals.css` sets `body { @apply bg-background text-foreground }` where `--background` is white.
**How to avoid:** Either add `.dark` class to `<html>` in auth layout, or change the CSS variable, or hardcode `bg-zinc-900` on the auth layout wrapper. **Recommended:** Hardcode `bg-zinc-900` on the layout div — no global CSS variable changes needed to avoid side effects.

### Pitfall 7: `register/page.tsx` and other auth pages not read
**What goes wrong:** The `register`, `forgot-password`, `reset-password`, `verify-email` pages were not read during research. They almost certainly share the same light palette as `login/page.tsx` but may have different form fields.
**Why it happens:** Didn't read all files to keep research lean.
**How to avoid:** Read each file before editing. Most auth form pattern changes are mechanical replacements — gray → zinc, blue → pastel blue.
