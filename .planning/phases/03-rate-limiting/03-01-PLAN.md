**A. Create `app/api/auth/login/route.ts`** (RATE-01 + RATE-05):
- Export `async function POST(request: Request)`
- Extract IP via `getClientIp(request)`
- Call `loginLimiter.limit(ip)` — if `!success`, return `NextResponse.json({ error: 'Demasiados intentos. Intenta de nuevo en unos minutos.' }, { status: 429, headers: { 'Retry-After': String(Math.ceil((reset - Date.now()) / 1000)) } })`
- Parse `{ email, password }` from `await request.json()`
- Call `const supabase = await createClient()` (from `@/lib/supabase/server`)
- Call `supabase.auth.signInWithPassword({ email, password })`
- On error: return `NextResponse.json({ error: error.message }, { status: 400 })`
- On success: return `NextResponse.json({ success: true })`
- IMPORTANT: The server-side `createClient()` uses `cookies()` from next/headers which automatically sets auth cookies via `Set-Cookie` headers on the Response. The browser fetch receives these cookies.

**B. Create `app/api/auth/forgot-password/route.ts`** (RATE-02 + RATE-05):
- Export `async function POST(request: Request)`
- Parse `{ email }` from request body
- Normalize identifier: `email.toLowerCase().trim()` (prevents case-sensitivity bypass — research Pitfall 4)
- Call `forgotPasswordLimiter.limit(identifier)` — if `!success`, return 429 with `{ error: 'Demasiadas solicitudes. Intenta de nuevo mas tarde.' }`
- Call `const supabase = await createClient()`
- Build `redirectTo`: `${process.env.NEXT_PUBLIC_SITE_URL ?? 'http://localhost:8080'}/auth/confirm?type=recovery&next=/reset-password`
- Call `supabase.auth.resetPasswordForEmail(email, { redirectTo })`
- ALWAYS return `{ success: true }` even if user not found — prevents email enumeration (research Pitfall 5). Only return error for actual server failures (non-"User not found" errors).

**C. Create `app/api/auth/resend-verification/route.ts`** (RATE-03 + RATE-05):
- Export `async function POST(request: Request)`
- Parse `{ email }` from request body
- Normalize identifier: `email.toLowerCase().trim()`
- Call `resendVerificationLimiter.limit(identifier)` — if `!success`, return 429 with `{ error: 'Demasiadas solicitudes. Intenta de nuevo mas tarde.' }`
- Call `const supabase = await createClient()`
- Call `supabase.auth.resend({ type: 'signup', email })`
- On error: return `NextResponse.json({ error: error.message }, { status: 400 })`
- On success: return `NextResponse.json({ success: true })`

**D. Update `middleware.ts`** (RATE-04 + RATE-05):
- Add imports: `import { callbackLimiter, getClientIp } from '@/lib/ratelimit/limiters'`
- At the TOP of the `middleware()` function, BEFORE `updateSession()`, add a check for `/callback`:
  ```
  if (request.nextUrl.pathname.startsWith('/callback')) {
    const ip = getClientIp(request);
    const { success } = await callbackLimiter.limit(ip);
    if (!success) {
      return NextResponse.redirect(new URL('/login?error=too_many_requests', request.url));
    }
  }
  ```
- Then fall through to existing `updateSession(request)` logic unchanged.
- Update the matcher regex to REMOVE the `callback|` exclusion. Change from:
  `'/((?!_next/static|_next/image|favicon.ico|api/|auth/confirm|callback|.*\\.(svg|png|jpg|jpeg|gif|webp)$).*)'`
  to:
  `'/((?!_next/static|_next/image|favicon.ico|api/|auth/confirm|.*\\.(svg|png|jpg|jpeg|gif|webp)$).*)'`
  This allows middleware to run on `/callback` for rate limiting. The rate limit check runs BEFORE `updateSession()` so the PKCE verifier concern (Phase 2 decision) is not affected — rate limiting does not call `getUser()`.
- IMPORTANT: After the rate limit check passes and falls through to `updateSession()`, the existing auth redirect logic will also run for `/callback`. The callback route is a route handler (not a page), so the `isDashboard` / `isAuthPage` checks won't match it — it falls through to `return response` which is correct. However, `updateSession()` will call `getUser()` before the callback route handler runs `exchangeCodeForSession()`. This was the original PKCE concern. To avoid this: add an early return after the rate limit check passes:
  ```
  if (request.nextUrl.pathname.startsWith('/callback')) {
    const ip = getClientIp(request);
    const { success } = await callbackLimiter.limit(ip);
    if (!success) {
      return NextResponse.redirect(new URL('/login?error=too_many_requests', request.url));
    }
    // Pass through without updateSession — callback handles its own auth
    return NextResponse.next();
  }
  ```
  This way, callback gets rate-limited but does NOT run through `updateSession()`, preserving the PKCE verifier.

- Also add `too_many_requests` to the login page error handling. In the existing login page errorParam check, `too_many_requests` should map to a rate limit message. This will be handled in Plan 02 when refactoring client pages.
